# Tests

- Unit tests (JUnit 5 + Mockito + AssertJ) in `src/test/java/.../unit/`, mirroring the main packages: **one test class per production class**, never grouping several classes in one test.
- Test names `method_scenario_expectedResult`.
- Controllers are tested with `@WebMvcTest` (MockMvc) and the proxy mocked with `@MockitoBean`: plain forwarding is verified with `eq(...)`, `isNull()` and `any(...)` on the six arguments of `forward` (`argThat` only for the `byte[]` body), the session routes only verify the delegation to the proxy method, plus the cases rejected before reaching it (CSRF, missing refresh cookie, no token). Proxies are tested against `StubHttpServer`, a local HTTP server that records what it receives (status, body and `Content-Type` passed through, `Accept-Language`/`Content-Type`/query forwarded, `internal-token` and `Authorization` absent, connection refused and timeout → `ServiceRequestException`); the specific methods (e.g. `OnboardingServiceProxy.createSession`) are tested the same way, with a snake_case `JsonMapper`, asserting what reached the target (path, body, `Content-Type`, `selected-*` headers) and the response built (status, body, `Set-Cookie` that write and clear the session).
- Black-box integration tests with REST Assured against the gateway running in Docker Compose (no Testcontainers), in `src/test/java/.../integration/`: `BaseIntegrationTest` (URL and ports from environment variables: `API_BASE_URL`, `API_PORT`, `MOCKSERVER_PORT`) and one class per route: `Test<Method><Action>` for routes that change something (e.g. `TestPostCreateLegalPerson`) and `Test<Method><Resource>` for GET routes, with no `Read` (e.g. `TestGetHealth`, `TestGetSession`). They run with `./mvnw test -Pintegration`; `./mvnw test` runs only the unit tests.
- The target services are played by the MockServer (see MockServer below). Each test asserts that status, body and `Content-Type` come back identical; a dropped connection is a template variant with `httpError` (`dropConnection`) instead of `httpResponse`.
- Integration test classes have no constants other than the route URL (e.g. `private static final String POST_LEGAL_PERSONS = "/legal_persons";`) and no helper methods of any visibility: each test declares its own data (names, documents, paths, tokens, timestamps), builds its own payload, makes its own call (REST Assured) and writes its own assertions inline, even when that repeats code across tests. Stateless tools (`JsonMapper`) are fine as instance fields, and `BaseIntegrationTest` keeps its shared constants and fields (URL, ports). Unit tests may keep constants, `@BeforeEach` setup and private helpers; instance fields for injected or per-test objects (`MockMvc`, mocks, a stub server opened in `@BeforeEach`) are fine.
- Request payloads in integration tests are declared in a single expression with `Map.of` and `List.of`, nested objects and lists included, never with `new HashMap<>()` plus `put`, `new ArrayList<>(List.of(...))` or JSON concatenated in a string. Above 10 entries use `Map.ofEntries(Map.entry(...), ...)`. `HashMap` is only for a test that needs an explicit `null` value or a mutable map. In TypeScript the equivalent is a typed object literal.
- Shared helpers (`MockTools`, `TokenTools`, `CsrfTools` and, when a test needs a prerequisite created through another route, `SetupTools`) live in `src/test/java/.../common/`, plus the expectation templates in `src/test/resources/expectations/`, and are the only reusable test code. The no-constants rule applies to them too, except for URLs and paths in `SetupTools`; stateless tools (`JsonMapper`) are fine as fields, and `MockTools` keeps only its configurable address (see MockServer).
- `SetupTools` methods receive the data the test needs to control, clear the MockServer before registering the expectations of the route they call, make the call and have a **single assertion, on the response status**, so a broken prerequisite fails at the setup line instead of later in the test. A test that uses `SetupTools` calls it first and only then its own `MockTools.clearMocker()`, followed by its expectations (`SetupTools...`, `MockTools.clearMocker()`, `MockTools.addExpectation(...)`). A test never relies on seed data.
- REST Assured must be 6.x: Spring Boot 4 brings Groovy 5 and Jackson 3, which REST Assured 5.x cannot use.
- Integration tests are always run against the real compose (`./infrastructure/service-start.sh test` + `./mvnw test -Pintegration`) before a task is closed.
- Each test generates its own data; no teardown.
- Every route has success and error tests, including the transport failure (500 `GEN00500`) and the CORS preflight.
- No comments in test code (`//`, `/* */`, Javadoc).

## Cookies and CSRF
- Integration tests authenticate with the `pulsepass_access_token` cookie (token signed by `TokenTools`) and never with `Authorization`; the refresh and logout routes also need the `pulsepass_refresh_token` cookie. A valid `Authorization: Bearer` without the cookie is 401.
- Every POST goes through CSRF. `CsrfTools.fetchToken()` calls `GET /actuator/health` (single assertion, status 200; any response carries the cookie through `CsrfCookieFilter`) and returns the `XSRF-TOKEN` cookie value; the test sends it as the `XSRF-TOKEN` cookie plus the `X-XSRF-TOKEN` header (`String csrf = CsrfTools.fetchToken();` is the first line of the test). Tests without the header, or with a different one, expect 403 `GEN00403` and no call to the MockServer.
- Session responses are asserted on the `Set-Cookie` headers (`response.headers().getValues("Set-Cookie")`): name, value, `Max-Age`, `Path`, `HttpOnly`, `Secure` and `SameSite=Strict`, and 204 with no body. A 403 for CSRF may carry an `XSRF-TOKEN` `Set-Cookie`, so do not assert that it has none.
- Unit tests with MockMvc do not use `jwt()` from `spring-security-test` either: it calls `CsrfFilter.skipRequest`, so CSRF is not checked and `CsrfCookieFilter` finds no token; an authenticated request sends a `pulsepass_access_token` cookie signed with `TokenTools.sign`.
- Unit tests with MockMvc do not use `csrf()` from `spring-security-test`: it replaces the `CsrfTokenRepository` of the shared filter chain for the following tests of the same context and breaks the ones that check the `XSRF-TOKEN` cookie. They send a literal `XSRF-TOKEN` cookie and `X-XSRF-TOKEN` header through a private `RequestPostProcessor`.

## Tokens
- The test key pair is the fixed development pair of the Keycloak realm: the private key is `src/test/resources/keys/jwt-private-key.pem` and the public key is in `JWT_PUBLIC_KEY` (`.env.example`) and in `src/test/resources/security-test.properties` for the unit tests with `SecurityConfiguration`.
- Tests sign RS256 tokens with Nimbus through `TokenTools` (`common/`): `sign(issuer, issuedAt, expiresAt, claims)` signs with the test key, `sign(signingKey, ...)` signs with another key, `signHmac(secret, ...)` signs HS256 and `unsigned(...)` builds an `alg=none` token (algorithm-confusion regressions), and `otherPrivateKey()` generates a key the gateway does not trust. The helper has no data: each test passes its issuer (`http://pulse-pass-keycloak:8080/realms/pulse-pass`), timestamps and claims (`person_key`, `legal_person_key`, `realm_access.roles`), so expired, wrong-issuer, tampered and foreign-key tokens are built inline in the test.
- Unit tests of controllers import `SecurityConfiguration` and `SecurityErrorHandler`, with `@TestPropertySource(locations = "classpath:security-test.properties")`; they authenticate with `jwt()` from `spring-security-test`. `SecurityConfigurationTest` uses real signed tokens, sent in the access cookie, to exercise the decoder.
- Every protected route is tested without token, tampered, expired, with another key, with the wrong issuer, with a role that is not allowed (403) and with each allowed role (the only role-protected routes are unknown ones and wrong-method calls, e.g. `GET /auth/logout`, since `POST /auth/logout` and `GET /auth/me` accept any valid token), and a public route is tested to work without any token and with an expired or tampered access cookie.

## MockServer
- Target services are played by the MockServer of the compose, driven by `MockTools` in `src/test/java/.../common/`: `clearMocker()`, `addExpectation(mockCode)`, `addExpectation(mockCode, pathParameters)`, `addExpectation(mockCode, pathParameters, expectationChanges)` and `retrieveRequests(method, path)`.
- Each external route has a default expectation in `src/test/resources/expectations/<api>/<method>-<name>.json`, in the MockServer format: `httpRequest` with `{param}` placeholders in the path and `httpResponse` with a realistic default body. Other responses of the same route are variants in their own file (`<method>-<name>_<variant>.json`, e.g. `onboarding-service/post-legal_persons_server_error.json`).
- `addExpectation` loads the template, sets `pathParameters` on the request and applies `expectationChanges` to the response: `payload` overrides keys of the body, `status_code` the status and `headers` the headers.
- Every integration test starts with `MockTools.clearMocker()` (right after its `SetupTools` calls, when it has any) and registers only the expectations it needs, with the values (ids, keys, tokens) declared in the test itself. No expectations in `@BeforeAll`, none shared between tests, and no `priority` or body matching to tell tests apart. Integration tests run sequentially because they share the MockServer.
- `MockTools` has no route-specific methods and no constants: paths live in the templates, and tests write the external paths inline in `retrieveRequests`.
