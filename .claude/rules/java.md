# Java code

## Structure
- Java 21, Spring Boot 4.x, Maven (no Gradle, no Lombok), no Spring Cloud Gateway. Package `com.pulsepass.backofficegateway`.
- Packages: `api` (controllers, configurations, exceptions) and `infrastructure/proxies` (`ServiceProxy`, `ServiceRequestException` and one folder per target service, with its `dtos` subfolder); `common` only when a language helper is needed.
- The gateway has no domain and no persistence, and it forwards requests raw (see Forwarding). It has DTOs only for the formats it reads from or writes to a target service, in `infrastructure/proxies/<service>/dtos`, named `<Service><Action>Request/Response` (e.g. `OnboardingServiceSessionResponse`: the onboarding login/refresh JSON with `access_token`, `expires_in`, `refresh_token`, `refresh_expires_in`, `token_type`; `OnboardingServiceRefreshTokenRequest`: `{"refresh_token": ...}`).
- `common/` holds only general-purpose language helpers (string, JSON, document math), named `<Subject>Handlers` (`JsonHandlers`, `DocumentHandlers`) and placed directly in `common/`, without a `utils` subfolder. Framework concerns (HTTP clients, timeouts, Spring beans) never go to `common/`: prefer the Spring Boot configuration (properties and auto-configured beans such as `RestClient.Builder`); what is left stays in the class that uses it.
- Always reference the object's own fields with `this.`.

## Method order
- Private methods always **before** public ones, in the order they are used.
- Prefer separate, clear `if`s over compound `||` conditions when each case has its own meaning.

## Code
- No comments in code, configuration, scripts or Dockerfile (Javadoc included): names and structure must explain the code, and decisions go to the rules, the README or the task notes. The only exceptions are the version next to a workflow action pinned by SHA and generated or third-party files kept as they come (`mvnw`, `checkstyle.xml`).
- No defensive validation (e.g. checking that a value from the environment is not empty); `try/catch` only around the call that actually throws (the HTTP call).
- Keep it simple: compare strings with `equals`, no `MessageDigest.isEqual` or similar tricks.
- `to*`/`from*` methods exist only in classes that represent data, converting themselves (`toDTO`, `toDomain`, static `fromDomain`/`fromEntity` in the services), and in the static helpers of `common/` (`toJson`). The gateway has no data classes, so its components (proxies, controllers, configurations, handlers) never have a `to*`/`from*` method: a private step that checks a value is `validate*` and returns nothing, and one that builds something is named after the action (`build*`, `copy*`).

## Forwarding
- `ServiceProxy` has a single public method, `forward(HttpMethod method, String path, HttpServletRequest request, MediaType contentType, byte[] body, Jwt jwt)`, which makes the HTTP call once (request, `try`, response mapping). A null `contentType` copies the client `Content-Type`; a non-null one overrides it (used by the bodies generated by the gateway, such as `{"refresh_token"}`). A null `jwt` is a public route, with no `selected-*` headers; a non-null one adds them. Private methods are only auxiliary steps, before the public one: `targetUri` and `copyHeaders(HttpServletRequest, MediaType, Jwt, HttpHeaders)`. `copyHeaders` copies `Content-Type` and `Accept-Language` from the client, then, in separate `if`s, replaces the `Content-Type` when `contentType` is not null and, inline when `jwt` is not null, sets `selected-user-key` (claim `person_key`), `selected-user-roles` (roles of `realm_access.roles` joined by comma) and `selected-agent-key` (claim `legal_person_key`, only when present), with the header and claim names written in place.
- Pure forwarding goes from the controller straight to `forward`; anything that interprets the target's response (status, body) is a named method of that target's `<Service>Proxy` (e.g. `OnboardingServiceProxy.createSession`), built on `forward`, and the controller calls it in one line. These methods receive the `HttpServletRequest` and the values they need, return `ResponseEntity<byte[]>`, and the proxy receives the `JsonMapper` in the constructor when it builds or reads JSON. The body generated by the gateway (refresh and logout) is `OnboardingServiceRefreshTokenRequest` serialized by the Spring `JsonMapper` (`{"refresh_token": "..."}`), sent with `contentType` `application/json`, so on those two routes the `Content-Type` is always `application/json`, whatever the client sent; login forwards the client body with `contentType` null, keeping the client `Content-Type`.
- Session exception to the raw forward, in `OnboardingServiceProxy`: `createSession` (`POST /auth/login`) forwards the client body and, when the target answers 200, reads the JSON into `OnboardingServiceSessionResponse`, writes the two session cookies and answers 204 with no body (any other status goes back raw). `refreshSession` (`POST /auth/refresh`) takes no client body: the controller reads the refresh cookie (`@CookieValue`, a missing one is `MissingRequestCookieException` → 401 `GEN00401` without calling the proxy), the proxy forwards the generated body, rewrites the cookies on 200 (204 no body) and clears both on 401 (raw response). The realm revokes the refresh token on every renewal (`revokeRefreshToken`, `refreshTokenMaxReuse` 0) and ends the whole session when a used one comes back, so every 200 must rewrite the refresh cookie and a 401 means the session is over; the gateway does not serialize refreshes, the `backoffice-app` does it across tabs with Web Locks. `deleteSession` (`POST /auth/logout`) also receives the refresh cookie, forwards the generated body with the `Jwt`, returns the target status and always clears both cookies. `GET /auth/me` is a plain forward with the `Jwt`, in the controller.
- One `<Service>Controller` per target service (e.g. `OnboardingController`) with explicit routes, and one `<Service>Proxy extends ServiceProxy` per target service (e.g. `OnboardingServiceProxy`). The controller calls `proxy.forward(method, path, request, null, body, null)` for plain forwarding and the session methods of the proxy for the session routes.
- The forward is raw, with no schema or DTO: the controller takes `HttpServletRequest` and `@RequestBody(required = false) byte[] body`; the body, the query string and the `Content-Type` and `Accept-Language` headers go to the target.
- `internal-token` and `Authorization` are never forwarded. `/<service>/internal/**` routes are never exposed.
- The response comes back as the target sent it: same status, same body (bytes) and same `Content-Type`, for any status (201, 400, 409, 415, 500...). The proxy uses `RestClient.exchange(...)`, which does not throw on 4xx/5xx.
- The gateway exposes routes without the service prefix (`POST /legal_persons`) and adds it when forwarding (`/onboarding/legal_persons`).
- The base URL comes from `app.<name>.url`, fed by the `<NAME>_URL` variable that `service-start.sh` resolves from the `<NAME>_TEST_URL` / `<NAME>_DEVELOPMENT_URL` pair. Timeouts come from `spring.http.clients.connect-timeout` and `spring.http.clients.read-timeout`, which Spring Boot applies to the auto-configured `RestClient.Builder`; proxies receive the builder injected and never build a request factory by hand. Redirects are not followed (`spring.http.clients.redirects=dont-follow`), so a 3xx of the target reaches the client as it was sent. An empty response body goes back as no body, so Spring does not invent a `Content-Type`.
- A transport failure (`RestClientException`: connection refused, DNS, timeout) is logged in the proxy (`ServiceProxy.forward - Request failed {service, method, path}`, exception as the last argument) and becomes `ServiceRequestException` → 500 `GEN00500` with the generic message. The `try` wraps only the HTTP call.
- CORS comes from `app.cors.allowed-origin` (`BACKOFFICE_APP_URL`), set in a `WebMvcConfigurer`; the security chain reuses it with `cors(Customizer.withDefaults())`, so the preflight is answered before authentication.

## Security
- The gateway validates the JWT locally (`spring-boot-starter-oauth2-resource-server`, stateless, no form login or basic auth) in `SecurityConfiguration`. The `JwtDecoder` is `NimbusJwtDecoder.withPublicKey` with the RSA public key of `app.security.jwt.public-key` (`JWT_PUBLIC_KEY`, base64 of the X.509 DER in one line) and the default validators plus the issuer of `app.security.jwt.issuer` (`JWT_ISSUER`). Keycloak is never called to validate a token.
- Public routes: `POST /legal_persons`, `POST /auth/login`, `POST /auth/refresh`, `OPTIONS /**` and `GET /actuator/health/**`, declared once as a `RequestMatcher` (`publicRoutes`) used both by `permitAll()` and by `CookieBearerTokenResolver`, which returns null on them: public routes ignore the session cookie, so an expired or invalid one there is not a 401. `POST /auth/logout` and `GET /auth/me` require only a valid token of any role (`authenticated()`), so a buyer who tried the backoffice can still end the session and read who they are. Everything else requires `ORGANIZER` or `ADMIN`; a new public route must be added explicitly to `publicRoutes`, never by loosening `anyRequest`.
- The session lives in `httpOnly` cookies managed by the gateway (BFF pattern): the browser never sees the tokens. `pulsepass_access_token` (`HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=expires_in`) and `pulsepass_refresh_token` (same attributes, `Path=/auth`, `Max-Age=refresh_expires_in`), built in `OnboardingServiceProxy` (private `buildCookie(name, value, path, maxAge)`, with `ResponseCookie`); clearing is the same name, path and attributes with `Max-Age=0` and an empty value. The names `pulsepass_access_token` and `pulsepass_refresh_token` are written in place where they are used (the proxy, `CookieBearerTokenResolver` and `@CookieValue`), with no constants, the same rule as the `selected-*` headers.
- The access token is read from the `pulsepass_access_token` cookie by `CookieBearerTokenResolver`; the `Authorization` header is no longer accepted (a valid Bearer without the cookie is 401). The `BearerTokenAuthenticationFilter` is registered by hand (`JwtAuthenticationProvider` + `ProviderManager`, `AuthenticationEntryPoint` and `AuthenticationEntryPointFailureHandler` = `SecurityErrorHandler`, added before `AuthorizationFilter`) instead of `oauth2ResourceServer(...)`, because that configurer adds every request that carries a bearer token to the CSRF ignore list, which would switch CSRF off for every request with the cookie.
- CSRF is on: `csrf(csrf -> csrf.spa())` (`CookieCsrfTokenRepository.withHttpOnlyFalse()` + SPA request handler; cookie `XSRF-TOKEN`, header `X-XSRF-TOKEN`), never `disable` or a matcher that skips it (`java:S4502`). The token is deferred by default, so `CsrfCookieFilter` (a `OncePerRequestFilter` registered with `addFilterAfter(new CsrfCookieFilter(), CsrfFilter.class)`) calls `getToken()` on every request: any response, a 401 included, carries the `XSRF-TOKEN` cookie, and there is no route just to fetch it. The front gets the cookie from its first call (`GET /auth/me` on hydration) and axios sends the header on every POST. A CSRF failure goes to the `AccessDeniedHandler` → 403 `GEN00403`; since the CSRF filter runs before authentication, a protected POST without CSRF and without session is 403, not 401.
- CORS allows credentials (`allowCredentials(true)`) with the explicit origin and the headers `Content-Type`, `Accept-Language` and `X-XSRF-TOKEN`.
- Roles come from `realm_access.roles` of the token and become `ROLE_<ROLE>` in `JwtRolesConverter`.
- A missing, malformed, expired, wrong-issuer or wrongly signed token is 401 `GEN00401` (`error.unauthorized`) and a valid token without the role is 403 `GEN00403` (`error.forbidden`). Both are written by `SecurityErrorHandler` (`AuthenticationEntryPoint` + `AccessDeniedHandler`) with the same `ErrorResponse` and `MessageSource` as the rest of the gateway, because they happen in the filter chain, before the controller advice.
- Authenticated routes receive `@AuthenticationPrincipal Jwt jwt` in the controller and call `proxy.forward(method, path, request, null, body, jwt)` (directly or through the service), which adds `selected-user-key` (claim `person_key`), `selected-user-roles` (roles joined by comma) and `selected-agent-key` (claim `legal_person_key`, only when present; the admin has none). Public routes pass a null `jwt`. `selected-*` headers sent by the client are never copied, and `Authorization` is never forwarded.
- Every token issued by the realm carries the `person_key` claim (the onboarding writes the attribute at self-registration, the admin seed has it, and the mapper is in the `onboarding-service` client), so a `forward` with a `Jwt` writes `selected-user-key` without checking for its absence (no defensive validation); only `legal_person_key` is optional.

## Errors
- Handlers take no `Locale` parameter; `build` reads the request language from `LocaleContextHolder.getLocale()` (fed by `Accept-Language`) to pick `messages.properties` or `messages_pt.properties`.
- Every error produced by the gateway goes through `build` and answers `ErrorResponse(title, message, code, extra_fields)`; `extra_fields` is always present, an empty list here. The gateway does not read the body, so it has no `GEN00400` or `GEN00415`; those come from the target service untouched.
- Never branch on types with `instanceof` (including pattern matching); write one method per type instead (e.g. one `@ExceptionHandler` per exception).
- Exception messages are plain literal text, no string concatenation.
- Codes: generic errors (schema validation, authentication, permission, unknown route or method, unsupported media type and unexpected failures) use `GEN` + the HTTP status (`GEN00400`, `GEN00401`, `GEN00403`, `GEN00404`, `GEN00405`, `GEN00415`, `GEN00500`). Authentication and permission exceptions (e.g. `UnauthorizedInternalRequestException`) are generic too: they use `GEN00401` / `GEN00403` and map to 401 / 403. Every other `DomainException` carries the service code `<SVC>0000N` (e.g. `ORG00001`, `ONB00006`) and maps to a 4xx status in the `STATUS_MAP`. Every `DomainException` must be mapped: the 500 default of `getOrDefault` exists only for a forgotten mapping, which is a bug. 500 is always `GEN00500` with the generic `error.internal` message. The gateway has no domain, so it only answers `GEN00404`, `GEN00405` and `GEN00500`; a transport failure to the target service is an unexpected failure (`GEN00500`).

## API
- Route paths start with the service name (`/onboarding/legal_persons`), in snake_case with underscores, never hyphens. Service-to-service routes live under `/<service>/internal/**` (e.g. `/organization/internal/organizations`) and are never exposed by the gateways. The gateways expose routes without the prefix and add it when forwarding.
- JSON in snake_case (`spring.jackson.property-naming-strategy=SNAKE_CASE`).
- Logs follow `ClassName.method - message`. The message is literal text; data goes in a single `Map` argument (`logger.error("X.y - Request failed {}", Map.of("service", name), e)`), never interpolated in the sentence. The exception is passed as the last argument, never `e.getMessage()`.
- Logs never contain the request or response body (it carries passwords and tokens), cookies, tokens, the `Authorization` header nor the query string; they only receive the single `Map` with the chosen fields. The only log is the transport failure in `ServiceProxy.forward`.
