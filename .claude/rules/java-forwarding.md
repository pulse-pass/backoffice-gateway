# Forwarding

## Raw forward

- **BGW-063** The forward is raw, with no schema or DTO: the controller takes `HttpServletRequest` and `@RequestBody(required = false) byte[] body`.
- **BGW-064** The body, the query string and the `Content-Type` and `Accept-Language` headers go to the target.
- **BGW-065** `ServiceProxy` has a single public method, `forward`, which makes the HTTP call once; its private methods are only auxiliary steps (`targetUri`, `copyHeaders`).
- **BGW-066** A null `contentType` copies the client `Content-Type`; a non-null one overrides it (used by the bodies generated by the gateway).
- **BGW-067** The response comes back as the target sent it: same status, same body (bytes) and same `Content-Type`, for any status (201, 400, 409, 415, 500...).
- **BGW-068** The proxy uses `RestClient.exchange(...)`, which does not throw on 4xx/5xx.
- **BGW-069** An empty response body goes back as no body, so Spring does not invent a `Content-Type`.
- **BGW-070** A gateway checks the transport failure, the response status and an empty body, and nothing else: it never validates the fields of a response one by one (`body.id() == null`), and it trusts the contract of the system it calls.
- **BGW-071** Redirects are not followed (`spring.http.clients.redirects=dont-follow`), so a 3xx of the target reaches the client as it was sent.
- **BGW-072** Path variables are always encoded with `UriUtils.encodePathSegment(value, StandardCharsets.UTF_8)` when building the forwarding path, so a decoded `?`, `/`, space or quote reaches the service as part of a single segment.
- **BGW-073** The gateway does not validate the format of path variables.
- **BGW-074** A transport failure (`RestClientException`: connection refused, DNS, timeout) is logged in the proxy (format in java-logs) and becomes `ServiceRequestException`.

## Proxies and controllers

- **BGW-075** One `<Service>Controller` per target service (e.g. `OnboardingController`) with explicit routes.
- **BGW-076** One `<Service>Proxy extends ServiceProxy` per target service (e.g. `OnboardingServiceProxy`).
- **BGW-077** Pure forwarding goes from the controller straight to `proxy.forward(...)`.
- **BGW-078** Anything that interprets the target's response (status, body) is a named method of that target's `<Service>Proxy` (e.g. `createSession`), built on `forward`, and the controller calls it in one line.
- **BGW-079** Those methods receive the `HttpServletRequest` and the values they need, and return `ResponseEntity<byte[]>`.
- **BGW-080** The proxy receives the `JsonMapper` in the constructor when it builds or reads JSON.
- **BGW-081** Timeouts come from `spring.http.clients.connect-timeout` and `spring.http.clients.read-timeout` in `application.properties`, which Spring Boot applies to the auto-configured `RestClient.Builder`.
- **BGW-082** Proxies receive the `RestClient.Builder` injected and never build a request factory by hand.
- **BGW-083** The base URL comes from the property `app.<name>.url`, fed by the `<NAME>_URL` variable that `service-start.sh` resolves from the `<NAME>_TEST_URL` / `<NAME>_DEVELOPMENT_URL` pair.

## Session routes

- **BGW-084** The body the gateway generates (refresh and logout) is `OnboardingServiceRefreshSessionRequest` serialized by the Spring `JsonMapper`, sent with `contentType` `application/json`, whatever the client sent.
- **BGW-085** `createSession` (`POST /auth/login`) forwards the client body with its `Content-Type`; any status other than 200 goes back raw.
- **BGW-086** On 200, `createSession` reads the JSON into `OnboardingServiceCreateSessionResponse`, writes the two session cookies and answers 204 with no body.
- **BGW-087** `refreshSession` (`POST /auth/refresh`) takes no client body: the controller reads the refresh cookie (`@CookieValue`) and the proxy forwards the generated body.
- **BGW-088** On 200, `refreshSession` rewrites both cookies (204, no body); on 401 it clears both and returns the target response; any other status goes back raw.
- **BGW-089** The realm revokes the refresh token on every renewal (`revokeRefreshToken`, `refreshTokenMaxReuse` 0) and ends the whole session when a used one comes back.
- **BGW-090** So every 200 must rewrite the refresh cookie, and a 401 means the session is over.
- **BGW-091** The gateway does not serialize refreshes; the `backoffice-app` does it across tabs with Web Locks.
- **BGW-092** `deleteSession` (`POST /auth/logout`) receives the refresh cookie, forwards the generated body with the `Jwt`, returns the target status and always clears both cookies.
- **BGW-093** `GET /auth/me` is a plain forward with the `Jwt`, in the controller.
